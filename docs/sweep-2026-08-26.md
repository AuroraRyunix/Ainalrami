# Codebase sweep, 2026-08-26

A deliberate read of Ainalrami looking for bugs, optimizations and things
worth adding, run at the same time as the OpenPairings half (which is in
that repo's `docs/sweep-2026-08-26.md`).

Nothing here has been fixed. This is the list.

## What it was aimed at

Two things. First, the shape that has produced every real bug in this
engine's recent history: **the same rule written down twice**, drifting.
`played?/1` was a private copy of `Trf.game_was_played?/1` that recognised
three result codes where the shared table recognised six;
`participated_in_pairing?/1` was an identical copy that had not drifted
*yet*.

Second, the harnesses **as instruments**. Three instrument bugs have been
found here before - a hardcoded `152 W` that inflated colour disputes, an
error page parsed as pairs, a three-way corpus weaker than the two-way one
- and an instrument that quietly stops measuring still reports 100%.

## The headline

The engine core came back clean of confirmed logic bugs. What did come back
is worth reading anyway:

* **`pair_later_round/2` never clears the process-dictionary state it
  sets**, and honours only two of `pair_next_round/2`'s four options. A
  caller using the documented public API gets stale state on the next call
  in the same process.
* **`explain_round/3` silently drops `opts[:point_system]`**, so the
  diagnostic scores a tournament by different values than the pairing did -
  the explanation can describe a round that was not produced.
* **Two harness instruments have drifted**: the JaVaFo comparison still
  counts engine refusals as illegal pairings (the fix landed only in the
  bbpPairings harness), and the taxonomy test's "deliberate copy" of the
  generator carries the hardcoded `152 W` that was fixed in the original.

## Bugs (5)

### pair_later_round/2 never clears the process-dictionary state it sets, and its own `||` fallback then leaks a previous tournament's forbidden pairs into the next call

`lib/ainalrami/pairing.ex:735`

`pair_next_round/2` wraps everything in `try/after` and deletes @expected_rounds_key, @initial_colour_key, @point_system_key, @played_key and @forbidden_key (pairing.ex:160-166). The public `pair_later_round/2` sets @expected_rounds_key (733) and @forbidden_key (735-740) with NO `after`, and `do_pair_later_round/1` sets @played_key (747) with no `after` either — only @bye_score_key/@round_matcher_key/@oracle_key/@dirty_key/@first_single_bye_key are cleaned (801-807). Because both puts fall back to `Process.get(...)` when the option is absent, the leftovers are not merely inert: the NEXT direct call inherits them.

Two distinct wrong answers follow. (a) A forbidden-pair map from tournament A silently forbids the same starting ranks in tournament B. (b) `expected_rounds` from A survives, so `final_round_topscorers?/2` (4027-4090) can admit a same-absolute-colour pair in a MID-tournament round of B — exactly the absolute-criterion breach `colour_compatible?/2` exists to prevent.

The repo's own test is one line-order away from catching it: score_reconciliation_test.exs:113-121 calls `pair_later_round(players)` (control) and then `pair_later_round(players, forbidden_pairs: [[1, 3]])`. Run in that order it passes; swapped, the "control" call inherits the map and raises NoValidPairingError. ExUnit's per-test process is the only thing hiding this today; the sibling Phoenix app noted at pairing.ex:4117 pairs from a long-lived process.

A related sharp edge in the same expression: `opts[:forbidden_pairs] && forbidden_map(...)` — passing `forbidden_pairs: []` yields `[]` (truthy) -> `forbidden_map([], _)` -> `nil` -> `|| Process.get(@forbidden_key)`, so an explicit "nothing is forbidden" does not clear a stale map, it inherits one.

**Evidence.** pairing.ex:733-742
    Process.put(@expected_rounds_key, opts[:expected_rounds] || Process.get(@expected_rounds_key))

    Process.put(
      @forbidden_key,
      (opts[:forbidden_pairs] &&
         forbidden_map(opts[:forbidden_pairs], rounds_played(players) + 1)) ||
        Process.get(@forbidden_key)
    )

    do_pair_later_round(players)

pairing.ex:801-807 (the only `after` on this path — @forbidden_key/@expected_rounds_key/@played_key absent)
      Process.delete(@bye_score_key)
      Process.delete(@round_matcher_key)
      Process.delete(@oracle_key)
      Process.delete(@dirty_key)
      Process.delete(@first_single_bye_key)

Concrete state:
  Pairing.pair_later_round(playersA, forbidden_pairs: [[1, 3]])   # puts %{1 => #MapSet<[1,3]>, 3 => #MapSet<[1,3]>}
  Pairing.pair_later_round(playersB)                              # nil || <A's map>  => B may not pair ranks 1 and 3

**Fix.** Wrap `pair_later_round/2`'s body in `try/after` and delete @expected_rounds_key, @forbidden_key and @played_key there, the way `pair_next_round/2` and `explain_round/3` already do. To keep the `pair_next_round/2` -> `pair_later_round/1` delegation working, have `pair_next_round/2` pass its resolved values down as opts (or call `do_pair_later_round/1` directly) instead of relying on the callee reading the dictionary it just wrote.


### explain_round/3 silently drops opts[:point_system], so the diagnostic scores a different ladder than the engine it is meant to adjudicate — and the CLI passes that option to both

`lib/ainalrami/pairing.ex:264`

`pair_next_round/2` stashes the point system (pairing.ex:131) and every score-dependent rule reads it through `result_points/1` (1108-1113) and `point_system/0` (1115-1117). `explain_round/3` stashes @expected_rounds_key, @initial_colour_key, @played_key and @forbidden_key but not @point_system_key, and does not read `opts[:point_system]` at all — so every one of those reads falls back to `Trf.default_point_system()`.

The CLI builds ONE keyword list, `pairing_opts/1` (cli.ex:297-318), containing `point_system: tournament[:point_system]`, and hands the same list to `Pairing.pair_next_round/2` (cli.ex:287, honours it) and to `Pairing.explain_round/3` (cli.ex:211, drops it). So `openpair file.trf -x` on any file with a `162`/`BB*` line pairs under the file's system and explains under 1/=/0.

What drifts, concretely, on a file with `BBL  0.5` (a loss worth half a point) and any player holding an `H` half-point bye:
  * engine:        result_points("H") = 0.5, point_system().loss = 0.5 -> `0.5 > 0.5` false -> float :none
  * explain_round: result_points("H") = 0.5, default loss = 0.0     -> `0.5 > 0.0` true  -> float :down
That player is reported as a downfloater the engine never saw, so the C14/C16/C18/C20 rungs of the explanation are for a history the pairing does not have. The comment at pairing.ex:966-976 records this exact mis-reading costing 88.62% of rounds when it was hardcoded in the engine.

It is not confined to floats. `bye_disqualifying?/1` (4135-4138) compares `result_points(result) >= point_system().win`, so under `BBW 2.0` explain_round disqualifies an `F` bye-holder from the bye where the engine does not; that feeds `eligible_for_bye?/1` -> `bye_assignee_score/2` (called at line 295) -> @bye_score_key and @first_single_bye_key, so the top rung ("C2/C4/C5 bye-eligibility") and C9 are scored against a bye score the engine never computed. `final_round_topscorers?/2`'s threshold (4085-4086) is wrong for the same reason.

This defeats the stated purpose: edge_rungs/6's comment (2821-2827) says "Keeping one definition is the point: a diagnostic that scored a reimplementation of the criteria would only ever tell you whether the two implementations agreed." One definition, two point systems, is the same failure by another route.

### Trf.serialize/2 raises on a forbidden-pair group that came from a `260` line — the XXP writer kept an inline `length/1` where its sibling uses the shared group_ids/1

`lib/ainalrami/trf.ex:508`

`tournament[:forbidden_pairs]` holds two shapes: a plain list of ranks from `XXP` (parse_xxp, trf.ex:1146) and `{ids, first, last}` from a round-limited `260` line (parse_260, trf.ex:1237-1242). `group_ids/1` (478-480) exists precisely to normalise them, and `numeric_forbidden_lines/2` (454-456) uses it. `forbidden_pair_lines/1` — the DEFAULT serialize path, taken whenever `opts[:numeric_extensions]` is falsy (extension_lines/4, trf.ex:395-397) — does not: it calls `length(&1)` directly on the group.

`length/1` is a BIF that requires a list, so `length({[1, 3], 2, 6})` raises ArgumentError. A parse -> serialize round trip on any file containing a `260` line crashes.

The repo already proves the tuple reaches that field: extension_lines_test.exs:253-256 asserts `parsed.tournament[:forbidden_pairs] == [{[1, 3], 2, 6}]`. Nothing then serializes it, and the fuzz harness only ever builds two-id plain lists (fuzz_tournament.ex:128 — "One forbidden opponent for each selected player, as a two-id `XXP`"), so no corpus run touches this path.

The @doc for `serialize/2` claims the opposite (trf.ex:326-328): "`tournament[:forbidden_pairs]` (a list of mutually-forbidden starting-rank GROUPS) becomes one `XXP` line per group. Both ... round-trip through `parse/1`."

Note a second-order problem the fix has to decide: `XXP` carries no round limit, so even after `group_ids/1` is applied a `260` group would be silently WIDENED from "rounds 2-6" to "never" — which is the mirror image of the expiry bug numeric_forbidden_lines/2's own comment (trf.ex:440-449) says was caught by diffing bbpPairings on both forms.

**Evidence.** trf.ex:504-510 (the crashing writer)
  defp forbidden_pair_lines(nil), do: []

  defp forbidden_pair_lines(groups) do
    groups
    |> Enum.reject(&(length(&1) < 2))
    |> Enum.map(&("XXP " <> Enum.join(&1, " ")))
  end

trf.ex:478-480 (the canonical accessor the sibling writer uses)
  defp group_ids({ids, _first, _last}) when is_list(ids), do: ids
  defp group_ids(ids) when is_list(ids), do: ids
  defp group_ids(_), do: []

trf.ex:395-397 (default path -> forbidden_pair_lines)
  defp extension_lines(t, players, _max_round, _) do
    acceleration_lines(players) ++ forbidden_pair_lines(t[:forbidden_pairs])
  end

Repro: Trf.parse(roster <> "260   2    6    1    3\r\n") |> Trf.serialize()
  ** (ArgumentError) errors were found at the given arguments:
     * 1st argument: not a list      (:erlang.length/1, from trf.ex:508)

**Fix.** Route `forbidden_pair_lines/1` through `group_ids/1` the way `numeric_forbidden_lines/2` does. Since `XXP` cannot express a round range, prefer emitting a `260` line for tuple-shaped groups even in the default mode (or reject/warn) rather than widening the ban to the whole tournament; add a parse -> serialize -> parse round-trip assertion for the `260` fixture already built at extension_lines_test.exs:253.


### Three-way harness refuses three Gacrux-unsafe axes but not PAIRING_FUZZ_POINT_SYSTEM, which Gacrux cannot read at all

`test/ainalrami/three_way_comparison_test.exs:184`

`refuse_unsupported_axes!/0` guards `PAIRING_FUZZ_FORBIDDEN_PCT`, `PAIRING_FUZZ_NUMERIC_EXT` and `PAIRING_FUZZ_ACCEL` on the stated grounds that Gacrux would otherwise "pair a DIFFERENT tournament" and every affected round would be recorded as the two references contradicting each other. `PAIRING_FUZZ_POINT_SYSTEM` (added later, 2026-08-24/25) has exactly that property and is not guarded.

The axis is fully wired into this harness: `begin!/3` stashes `:fuzz_point_system`, `build_trf/3` emits the `BB*` lines through `Trf.serialize`, and `safely_pair/3` passes `point_system: point_system()` to `Pairing`. So bbpPairings and Ainalrami both see the non-standard scoring and Gacrux does not.

Verified against the sibling checkout, not assumed:

  * `grep -rn 'BBW|BBD|BBL|BBZ|BBF|BBU' ../TieBreakServer/` returns **zero hits** across the whole tree. Gacrux has no reader for any of the six lines this project writes.
  * Instead it brute-force *solves* a point system from the recorded totals (`scoresystem.py:solve_scoresystem_p`) over a bounded grid: `loss in {0.0, 0.5, 1.0}`, `draw in loss+{0.5, 1.0, 1.5, 2.0}`, `win in {2*draw-loss, +1, +0.5, +1.0, +1.5, +2.0}`. Two of the eight named systems in `@point_systems` fall outside that grid entirely - `draw_heavy` (win 1.0 with draw 2.0 needs win >= 4.0) and `paid_loss` (draw 0.5 with loss 0.5 needs draw >= 1.0) - and `paid_forfeit`'s `Z` value is never a free variable in the solver at all.

A point system decides scores, scores decide brackets, brackets decide everything after, so every round of such a run is Gacrux answering a different question. The single number this harness exists to produce - how far the two references agree - is then computed on a population where one reference was handed a different tournament. This is the same shape as the 42.23% acceleration result the moduledoc catalogues at length.

**Evidence.** test/ainalrami/three_way_comparison_test.exs:184-224

  defp refuse_unsupported_axes! do
    forbidden = env_int("PAIRING_FUZZ_FORBIDDEN_PCT", 0)
    numeric = System.get_env("PAIRING_FUZZ_NUMERIC_EXT")
    accel = System.get_env("PAIRING_FUZZ_ACCEL")
    # ... no read of PAIRING_FUZZ_POINT_SYSTEM anywhere in the module

Reachability, same file:
  227:  {rounds, player_count, forbidden, roster} = begin!(seed, rounds, player_range)   # stashes :fuzz_point_system
  232:  trf = build_trf(ps, rounds, forbidden)                                            # emits BBW/BBD/BBL/BBZ/BBF/BBU
  322:  point_system: point_system()                                                      # Ainalrami told the same system

Concrete input: PAIRING_FUZZ_POINT_SYSTEM=football PAIRING_FUZZ_COUNT=200 mix test --only three_way
  -> file carries `BBW  3.0` / `BBD  1.0` / `BBU  3.0`
  -> bbpPairings reads them (trf.cpp:1204-1230, `result.pointsForWin = readPoints(line)`)
  -> Gacrux ignores them and solves win=3 only if the totals happen to pin it; on `draw_heavy` / `paid_loss` no grid point fits at all

**Fix.** Add a fourth clause to `refuse_unsupported_axes!/0`: raise when `System.get_env("PAIRING_FUZZ_POINT_SYSTEM")` is set to anything other than nil/""/"standard", with the same wording as the other three ("Gacrux reads no BB* line and solves its own point system from a bounded grid; run this axis two-way"). Worth adding a covering test that asserts each named axis in the refuse list actually raises, so the next axis added to FuzzTournament has to be classified rather than silently inherited.


### Withdrawal byes skip result_points/1 while requested byes apply it - the harness writes a TRF bbpPairings rejects

`test/support/fuzz_tournament.ex:356`

`assign_requested_byes/1` writes the same `Z` result down two branches and scores it only on one. The withdrawal branch appends the game and leaves `points` alone; the requested-bye branch twelve lines below does `points: player.points + result_points(result)`. That is the same rule written twice with one copy missing the point-system term.

Harmless on every point system except one. `paid_forfeit` is `%{forfeit_loss: 0.5, zero_point_bye: 0.5}`, and `Trf.points_for/2` routes `"Z"` to `points.zero_point_bye` (trf.ex:202). `PAIRING_FUZZ_POINT_SYSTEM=mixed` draws it 1 time in 8, per tournament.

### -c counts a pending round as completed: any TRF with a pre-recorded bye for the unpaired round reports a false DIFFERS and exits 1

`lib/ainalrami/cli.ex:412`

`completed_rounds/1` restates "how many rounds are done" as `max(length(games))`. Everywhere else in the codebase that question goes through `Trf.participated_in_pairing?/1` - `Pairing.rounds_played/1` (pairing.ex:857), `Test.Field.rounds_played/1` - specifically so that an arbiter-recorded `H`/`Z` cannot drag the round number forward. `Ainalrami.Test.Field`'s moduledoc spends a section on why that distinction is load-bearing ("one player's pre-recorded bye cannot drag the round number forward and strand everyone else"). The checker does not use it, and the rule has drifted.

Consequence on a real mid-tournament file. An arbiter grants player 7 a half-point bye for round 6 and records it before round 6 is paired - the standard way a TRF expresses this, and exactly the shape `FuzzTournament.build_trf/3` hands both engines every round with `PAIRING_FUZZ_BYE_PCT>0`. `Trf.parse/1` derives the game count from the trimmed line length (trf.ex:1412-1423), so player 7 comes back with 6 games while everyone else has 5.

  * `completed_rounds/1` returns 6.
  * `check_round(parsed, 6)`: `recorded_pairs/2` reads `Enum.at(games, 5)` per player - nil for everyone but player 7, and player 7's is not `participated_in_pairing?` - so `actual = []`.
  * `state_before_round/3` builds exactly the position round 6 is to be paired from, so `expected` is a full pairing.
  * `composition([]) != composition(expected)` -> `Log.warn("round 6: DIFFERS")`, `differing = 1`, exit code 1.

So `ainalrami live.trf -c` fails on a file whose every completed round matched. The same restatement appears in `report_roster/1` (line 527), which makes `-p` log "pairing round 7" while `Pairing` correctly pairs round 6.

Honest caveat: `cli_test.exs:532-556` pins the current behaviour on the round-1 form of this case, with the rationale "Round 1 as recorded has nobody paired at all, so it differs". That rationale does not cover the mid-tournament form, where earlier rounds are genuinely complete and the exit code is what a caller keys off.

### A truncated RTG tournament declares a round count it was not paired under, so -g output is not self-checking as the README claims

`lib/ainalrami/generator.ex:118`

`generate/1` pairs the tournament with `expected_rounds: total_rounds` — the requested (or `players - 1`-capped) count — but writes `number_of_rounds: played_rounds` into both TRF16's `142` field and the `XXR` line. When generation halts early on `NoValidPairingError`, those two numbers differ, and the difference lands on the one rule that reads them.

`final_round_topscorers?/2` gates on `played_rounds >= expected_rounds - 1`. Concretely, with `--players=20 --rounds=9` on a seed that deadlocks entering round 5:

- During generation, round 4 is paired with played=3, expected=9 → `3 >= 8` is false → the final-round path is off, so C3's topscorer exemption cannot fire and the C10/C11 rungs stay constant.
- The file is then written with `142 = 4` and `XXR 4`.
- Any reader replaying round 4 — including `ainalrami file.trf -c` — computes played=3, expected=4 → `3 >= 3` is **true** → the final-round path is on.

So the last round of every truncated RTG file was paired under a different regime than the file says it was. It bites only when that round contains two topscorers holding the same absolute colour preference (or reaches C10/C11), which is why it has not been noticed; it is silent otherwise.

The unverified link is frequency: I have not run it (forbidden here), so I cannot say how often a truncated `-g` run lands on a topscorer clash. The mechanism itself is unconditional. Note the cross-program harness is NOT affected — both engines read the same file, so they agree with each other; this is a `-g`/`-c` self-consistency defect, and `-g`/`-c` are exactly the two modes FE1's auto-test invokes.

The README states the opposite without qualification: "The two modes are each other's test: `-g` output fed to `-c` checks clean by construction."

**Evidence.** lib/ainalrami/generator.ex:100 `|> play_one_round(rounds, forfeit_pct, forbidden, initial_colour)` and :236 `Pairing.pair_next_round(players, expected_rounds: total_rounds, ...)` vs :118 `number_of_rounds: played_rounds` and :123 `<> "XXR #{played_rounds}\r\n"`; :104 `Pairing.NoValidPairingError -> {:halt, {current, round_no - 1}}`. Gate at lib/ainalrami/pairing.ex:4088 `played_rounds >= expected_rounds - 1 and (a.points > threshold or b.points > threshold)`. Claim at README.md:218.

**Fix.** Either re-pair the final round under the round count that will be written, or pass `expected_rounds: played_rounds`-consistent state through the reduce; failing that, qualify the README claim to non-truncated runs.

## Optimizations (2)

### legal_pair?/2 rescans the whole game list (with a String.trim per game) on every candidate edge — wants a per-round MapSet

`lib/ainalrami/pairing.ex:3982`

```elixir
# pairing.ex:3982
defp legal_pair?(p1, p2) do
  not forbidden_pair?(p1.rank, p2.rank) and
    not Enum.any?(p1.games, &(played?(&1) and &1.opponent_rank == p2.rank))
end
```

`played?/1` delegates to `Ainalrami.Trf.game_was_played?/1` (pairing.ex:3834), which is:

```elixir
# trf.ex:215
def game_was_played?(result),
  do: result not in ~w(+ - H F U Z) and String.trim(result) != ""
```

So each `legal_pair?` call is an O(rounds-played) list traversal with a cross-module call and a `String.trim/1` per element. It is the C1 rematch test, invoked from at least five sites, several of them O(n²) or O(m²) per round:

* `bracket_edge_weight/8` → `base_edge_weights/8` (pairing.ex:2812, 2768) — every pair in the bracket window, and `base_edge_weights` is re-run at each bracket boundary (pairing.ex:2028, 2033)
* the whole-field repair matching (pairing.ex:1370) — a full `0..n-2 × i+1..n-1` double loop over the field
* `build_oracle/3` (pairing.ex:2246) — per round over the whole field
* `floats_placeable?/3` (pairing.ex:1901) — bracket × next-group, inside the eligibility test
* `stand_in_edges/8` (pairing.ex:1943)

The played-opponent set is a pure function of the player's games and does not change during a round — `do_pair_later_round/1` already stamps derived per-round state onto each player at pairing.ex:751-758 (`with_float_history/2` writes `:floats`), so there is an established place to put it.

The rationale comments here (pairing.ex:3961-3981) are entirely about *semantics* — which games forbid a rematch, and why the XXP exclusion lives in the same test. They say nothing about the list scan being deliberate, so this is not a documented trade-off.

**Evidence.** pairing.ex:3982-3985 (the O(games) scan); pairing.ex:3834 (`played?/1` → remote call); trf.ex:215-216 (`String.trim/1` per game); call sites at pairing.ex:1370, 1901, 1943, 2246, 2812.

Concrete: 100-player field, 9 rounds played. The repair matching at pairing.ex:1367-1370 alone evaluates 4,950 pairs × up to 9 games = ~44,550 `game_was_played?` calls, each with a `String.trim/1`. `build_oracle/3` and every bracket's `base_edge_weights/8` add more on top, per round. At the fuzz harness's measured ~12 tournaments/s this is a first-order term.

**Fix.** In `with_float_history/2` (or alongside it in `do_pair_later_round/1`, pairing.ex:745-758), stamp `:played_opponents => MapSet.new(for g <- player.games, played?(g), g.opponent_rank != nil, do: g.opponent_rank)` on each player, then `legal_pair?/2` becomes `not forbidden_pair?(...) and not MapSet.member?(p1.played_opponents, p2.rank)`. Semantics are unchanged (same `played?` predicate, same rank comparison). Expected: the C1 test drops from O(rounds) with a string trim per element to one O(1) lookup — roughly a 9-11x cut in that function's cost at typical round counts, multiplied by the O(n²) call volume. `pair_next_round/2`'s round-1 fast path (pairing.ex:151) is unaffected since those players have no games.


### score_before/3 recomputes reconciled_points/2 four times per player per round

`lib/ainalrami/pairing.ex:1031`

```elixir
# pairing.ex:1031
defp score_before(player, rounds_back, played) do
  from = max(played - rounds_back, 0)

  player.games
  |> Enum.slice(from, played - from)
  |> Enum.reduce(reconciled_points(player, played), fn game, score ->   # <-- line 1048
    score - result_points(game.result)
  end)
  |> Kernel.+(acceleration_at(player, played - rounds_back))
end
```

`reconciled_points(player, played)` (pairing.ex:1071) is a pure function of `(player, played)` — but it is evaluated fresh inside every `score_before/3` call. It walks the game list twice (`Enum.take(played)` then `Enum.drop(played)`), calling `result_points/1` per game, and `result_points/1` is a `Process.get(@point_system_key)` dictionary read per element (pairing.ex:1108-1113).

`with_float_history/2` (pairing.ex:944) calls `float_direction/4` twice per player, and each of those calls `score_before/3` twice (pairing.ex:1002-1003, for the player and the opponent) — so `reconciled_points/2` runs 4N times per round where N distinct values exist. That is 4 × N × R `Process.get` calls plus 4N four-candidate `Enum.find` passes, three quarters of which are redundant.

Smaller than the `legal_pair?` finding — this is once per round, not per edge — but it is on the same per-round rebuild path and the fix is trivial.

**Evidence.** pairing.ex:1048 `Enum.reduce(reconciled_points(player, played), ...)`; pairing.ex:1071-1094 `reconciled_points/2` walking the games twice with a `Process.get` per element via `result_points/1` (pairing.ex:1108-1113); pairing.ex:944-953 `with_float_history/2` producing 4 `score_before/3` calls per player; pairing.ex:1002-1003 the two calls inside `float_direction/4`.

Concrete: 200-player field, 11 rounds → 800 `reconciled_points/2` evaluations per round, ~17,600 `Process.get` calls, where 200 evaluations / ~4,400 reads would do.

**Fix.** Stamp the reconciled base on each player in `with_float_history/2` alongside `:floats` (it already has `played` in scope) and have `score_before/3` read it. Independently, hoist the point system out of the process dictionary for the duration of a round — reading it once and threading it into `result_points/2` removes a dictionary lookup from the innermost loop of `reconciled_points/2`, `score_before/3` and `float_direction/4`.

### CLI: a mistyped or space-separated option is silently ignored, and for -g that means a run that is not the run you asked for

`lib/ainalrami/cli.ex:48`

`split_flags/1` partitions argv into flags (a fixed list of bare flags, or anything matching `~r/^--[a-z-]+=/`) and positional. Nothing validates the flag names, so:

- `--player=30` (singular typo) lands in flags, matches nothing in `generate/1`, and the run uses the default `Enum.random(10..60)`. No message.
- `--seed=abc` → `option/2` returns nil via the `{value, ""}` guard → a random seed. No message.
- `--acceleration=bakku` → `acceleration_option/1` returns nil → no acceleration. The comment calls this deliberate ("treated as absent, which is the same silence `option/2` gives an unparsable integer") — consistent, but consistent silence.
- `--initial-colour=x` → `normalise_colour/1` returns nil → `Enum.find_value(flags, "w", ...)` falls through to the White default, so a typo silently picks a colour.
- Worst: `ainalrami -g out.trf --seed 42` (space instead of `=`). `--seed` matches neither the bare-flag list nor the `=` regex, so both `--seed` and `42` become positional. `generate/1` writes to `hd(positional)` and ignores the rest — the file is written, the seed is ignored, and the run is unreproducible.

The cost is specific to what this tool is for. The RTG's whole value proposition, argued at length in the TEC feedback draft's B.4, is that "reproducibility from an explicit seed is essential for debugging: we write the seed into the generated tournament's name so that a file always reproduces itself". A silently-dropped `--seed` produces a file that reproduces itself and is not the tournament you meant to generate — and the mistake is invisible unless you read the reported seed line back.

The fix is small and does not require adopting OptionParser: keep `split_flags/1`, add a known-option list, and `usage_error/1` on anything not in it. The exit path already exists.

**Evidence.** lib/ainalrami/cli.ex:48-53 `known_bare_flags = ~w(-p -g -c -x --explain -q --quiet -d --debug -h --help --version); Enum.split_with(argv, &(&1 in known_bare_flags or &1 =~ ~r/^--[a-z-]+=/))`; :85-96 `option/2` returning nil on any unparsable value; :67-73 `Enum.find_value(flags, "w", ...)`; :120-131 `generate/1` writing to `hd(positional)`.

**Fix.** Add a known-option allowlist to split_flags/1 and route unknown flags, unparsable values and bare `--opt value` forms through usage_error/1.


### Three-way harness has full colour data and no colour instrument, the gap that hid a missing Article 5.2.4 for 195 million pairings

`test/ainalrami/three_way_comparison_test.exs:330`

The two-way harness carries a 50-line rationale for why that was not good enough: "Every rate this harness has ever reported is colour-blind ... 4.3 million tournaments and 195 million pairings validated who plays whom and never once checked Article 5. The three-way harness has strictly more information available - two references' colour assignments on the identical position, which is what would let a colour difference be adjudicated by majority rather than filed as a known dispute - and uses none of it. ### Gacrux is already installed and used for pairings only — its tie-break half is the untested surface VCL.19 actually asks about

`test/support/gacrux.ex:3`

The highest-leverage unexploited asset across both repos. `Ainalrami.Test.Gacrux` shells out to `pairingchecker.py` in a checkout of Otto Milvang's **TieBreakServer** — located via `GACRUX_DIR`, defaulting to `../TieBreakServer`. The repo is named after the half nobody is calling.

The asymmetry is stark. Pairings have three independent implementations cross-checked over 2.5 billion individual pairings. Tie-breaks — BH, BHC1, BHC2, MBH, SB, DE, WIN/WON, BPG, PS, KS, ARO, AROC1, all of C.07 including Article 16's unplayed-game handling and the new 16.5.1 Cut-1 Exception — have `standings_test.exs` and nothing else. VCL.19 asks for "every included tiebreak tested against the FIDE Handbook's own rules", and docs/fide-endorsement.md rates it only "Substantially" satisfied.

What makes this practical rather than aspirational:
- The reference is already on disk for anyone running the three-way tests, with a known invocation pattern and a parser (`parse_output/1`) to copy.
- Ainalrami's `-g` mode produces complete tournaments with results, which is exactly the input a tie-break checker wants — no new fixture generation needed.
- OpenPairings' `TrfExport` already emits FIDE-submission-grade TRF16, so the file handed to Gacrux is the same one an arbiter would submit.
- The two known-weak spots have concrete predictions to test against: ARO with unrated opponents (see the Q208 finding), and Art. 16.3's trailing-voluntary-unplayed treatment, which `adjusted_score/3` implements from the handbook text alone.

One architectural note the TEC feedback draft already raises (B.3): tie-breaks live in OpenPairings, pairings in Ainalrami, so this test crosses the repo boundary. It probably belongs in OpenPairings' test suite with Gacrux gated the way `:javafo`/`:bbppairings`/`:swar_fixture` already are.

**Evidence.** test/support/gacrux.ex:3-6 "Thin wrapper for invoking Otto Milvang's `pairingchecker.py` (the pairing half of the FIDE Tie Break Server, gacrux.no)" and :38 `def dir_path, do: System.get_env("GACRUX_DIR", "../TieBreakServer")`. `grep -rn -i "tiebreak\|buchholz" lib/` in the Ainalrami repo returns nothing.

**Fix.** Add a Gacrux tie-break comparison to OpenPairings' test suite, gated like the existing :javafo tag, fed by -g-generated completed tournaments exported through TrfExport.
