# Codebase sweep, 2026-09-01

A deliberate read of the whole of Ainalrami looking for bugs, security
problems and things that are not optimal, run alongside the OpenPairings
half (in that repository's `docs/sweep-2026-09-01.md`). Two broad-scope
readers - one over the engine core (`pairing.ex`, `weighted_matching.ex`,
`matching.ex`, `sequence.ex`, `log.ex`), one over the input surface, CLI
and team pairing (`trf.ex`, `cli.ex`, `generator.ex`, `team_pairing.ex`
and its four modules, the test harness adapters) - each told to hunt where
the corpus cannot reach and to default to "not a finding". **Every claim
below was checked against the source by the orchestrator**, and every
finding in the I/O half was reproduced by execution before it was filed,
not inferred from reading.

The engine core came back the way it did in August: clean of confirmed
logic bugs. What the sweep found is almost entirely at the edges - the
parser reading a file somebody else wrote, the CLI being handed an
ordinary-looking argument, and the newer team engine's cost model.

Baseline on `feature/team-pairing` at `84caab5`: `mix compile
--warnings-as-errors` clean, **360 tests pass, 4 excluded** (the JaVaFo
and bbpPairings comparisons, binaries not present).

## What the corpus cannot see

The August sweep's own lesson was "not a rule implemented wrongly, but one
the corpus is structurally unable to produce". This sweep found the next
one, and it is not a rule at all: **`Generator` only ever writes ASCII
names.** Every one of the ~488M validated pairings went through a TRF the
engine wrote and read itself, with `Player123`-style names, so the
grapheme-vs-byte column question (H1) was never asked. bbpPairings reads
bytes; JaVaFo reads Java chars; this engine reads graphemes. On ASCII the
three agree. On "Đurić" they do not, and the harness compares outputs, not
column alignment. The fix for H1 is in `trf.ex`; the fix for the blind spot
is a generator axis with non-ASCII names, so it stays fixed.

## The three worth reading first

**H1.** `read/2` is `String.slice(line, start - 1, width) |> String.trim()`.
`String.slice/3` counts graphemes. A writer that counts bytes - the format's
own definition of a column, and what Swiss-Manager and bbpPairings do -
pads a 33-byte name field to 33 bytes; with "Björn" in it that is 32
graphemes, so every field after the name is read one column early. The
rating reads `200` for `2200`, the federation `ER` for `GER`, and the
round-1 block's colour and result columns land on the wrong characters and
parse as `nil` - which downstream is indistinguishable from "paired, not
yet played". A completed game becomes a phantom incomplete round with no
error. OpenPairings' TRF import delegates to this parser, so a
Swiss-Manager file with one accented name imports wrong there too.

**H3.** `write_pairs/2` is `File.write!(output_path, output_text)` with no
check that `output_path` differs from the input. `-p`'s output is not a
TRF, it is JaVaFo's bare board list. `ainalrami live.trf -p live.trf` -
the natural spelling of "pair the next round into this file" - replaces a
361-byte tournament with `2\n1 3\n4 2\n`, exit code 0. `-g` has the same
shape at `:221`.

**H2.** `report_extensions/1` does `Enum.map_join(group, " / ", …)` on each
forbidden-pair group. A `260` line parses to `{ids, first, last}`; a tuple
is not enumerable; `Protocol.UndefinedError` propagates through `run/1`,
which rescues only `{:usage, _}`. The August sweep's fix for this exact
shape in `Trf.serialize/2` (`4dd9980`) documented this call site as
sharing the defect. `Trf.group_ids/1` (`trf.ex:671-672`) is the
normaliser, and it is private.

## Findings

### H1 · Columns by grapheme

`trf.ex:1704` (`read/2`); `place/4` at `:909` pads the same way on the
write side, so an Ainalrami→Ainalrami round trip is self-consistent. The
reader reproduced the misread with a byte-padded "Björn" row: line 99
bytes / 98 graphemes; `fide_rating` 200, federation `"ER"`, round-1
`%{result: nil, colour: nil, opponent_rank: 2}`.

Fix: read lines as bytes and index columns by byte offset - that is what
the specification and every other implementation mean by "column" - or,
at minimum, detect a name field whose byte length differs from its
grapheme length and refuse rather than misread. The write side already
has an opt-in ASCII fold (`maybe_fold_ascii/2`, `:956`); the read side has
nothing.

### H2 · The CLI crashes on a `260` line

`cli.ex:402-405`. Reproduced for `-p` and `-x`: `protocol Enumerable not
implemented for Tuple. Got value: {[1, 3], 1, 3}`.

Fix: expose `Trf.group_ids/1` (or match the tuple in place) before the
join, and a CLI-level test on a `260` file - the code-only fix in August is
how this half was missed.

### H3 · Same input and output path destroys the tournament

`cli.ex:601-616` (`write_pairs/2`), `:213-225` (`generate/2`). Reproduced:
361 bytes → 13 bytes, exit 0.

Fix: refuse when the output path resolves to the input path (compare
`Path.expand/1` of both), and consider writing through a temp file and
rename so a failed write cannot leave a half-file either.

### H4 · A BOM drops line one

`trf.ex:1171`: dispatch is `String.slice(line, 0, 3)`; a BOM makes the
first line's code `"﻿00"`, which matches nothing and falls through
`parse_header_line/3` unchanged. Reproduced: a two-player file saved with a
BOM parses one player; a BOM before `012` loses the tournament name.
Windows Notepad writes this by default, and this project ships a Windows
binary.

Fix: `String.trim_leading(text, "﻿")` once, before splitting.

### H5 · A truncated opponent number reads as a shorter one

`trf.ex:1771-1780`: `round_count = div(trimmed_length - round1_start, 10)
+ 1` counts a partial block as a round, and `read/2` on a short line
returns what is there. Reproduced: opponent `2034` → `20` at 93
characters, `2` at 92. A different real player, or a dangling reference
that `validate_games!/2` documents as not an error. bbpPairings' reader
requires a full block (`startIndex <= line.size() - 8u`), which this file's
own `render/1` comment cites.

Fix: a round is present only if its whole block is; otherwise stop, or
raise.

### H6 · Team pairing's budget cannot bound the infeasible case

`team_pairing/bracket.ex:65-123`: `state.candidates` is incremented only in
`score_candidate/3`, reached only for a complete legal pairing. Proving
that none exists is bounded only by `completable?/3`'s pruning, which is
sound (verified) but not tight. Measured on a structured infeasible
bracket: **181 ms at 16 teams, 5.1 s at 20** - a 25% larger bracket, 28×
the time - with the default budget never engaging. Round one is one
bracket containing the whole field. Not shipped in OpenPairings yet (team
tournaments are parked), so no user is exposed today.

Fix: a node or step budget alongside the candidate budget, returning
`{:error, :budget_exhausted}` the way the individual engine's `grow/1`
raises past `4n+20`; and the conformance doc's "if it is ever slow, the
pruning is wrong" claim needs a measured bound behind it.

### M1 · Free-vertex tie-break on map order

`weighted_matching.ex:1775-1786` (`min_free_or_zero_to_outer/1`),
`:1718-1733` (`scan_row/5`), `:1737-1740` (`offer/4`): all keep the first
visited on a tie (`r < best`, `best <= r`), and the fold is over
`state.best_outer`, a plain map. The cross table was given a canonical
`{r, a, b}` order in the commit its own comment describes at `:1895-1900`
("first offered wins … an accident of iteration order"); this consumer
was not. Erlang map order is deterministic for one key set on one OTP,
so a machine reproduces itself - but not across OTP releases, nor across
the 32-key flatmap/hashmap boundary. Every candidate the tie is between
is equally legal; this is reproducibility, not conformance. It is
structurally common rather than rare while Article 4.3's exchange order
is not yet in the edge weight (see `TODO.md`).

Fix: break ties on `{r, v}` as the cross table does; then L5's docstring
becomes true again.

### M2 · Generator ranges run backwards

`generator.ex:94` (`1..rounds`) and `:143` (`1..count`): Elixir's
`first..last` steps by -1 when `last < first`, so `1..0` is two rounds and
`1..-5` is seven players with ranks down to -5. Reproduced through the
CLI: `--players=-5` writes `062 7`, `142 -6`, rows for ranks `1, 0, -1 …
-5`, exit 0. The 2026-08-29 options fix checked format, not range.

Fix: `1..n//1` where `n` may be ≤ 0, and reject non-positive `:players`
and `:rounds` in `generate/1`.

### M3 · `initial_colour` outside four strings crashes `serialize/2`

`trf.ex:814-816`: three clauses, no catch-all. `"black"` - which
`CLI.normalise_colour/1` accepts as input - crashes with
`FunctionClauseError` from `serialize/2` and from `Generator.generate/1`
(whose `:initial_colour` option is undocumented and unvalidated).
Reproduced three ways.

Fix: normalise as the CLI does, or raise `Trf.ValidationError`.

### M4 · A blank `142` is an assertion of zero rounds

`trf.ex:1732`: `parse_int(value) || 0` before
`check_round_count_agreement!/2`; `parse_xxr/2` leaves the accumulator
alone on a malformed value. Reproduced: `XXR 9` + blank `142` raises "two
different round counts (9 and 0)"; blank `142` alone yields
`number_of_rounds: 0` silently.

Fix: the same rule as `XXR` - an unparsable value is no assertion.

### M5 · Two public team-pairing functions crash on caller input

`team_pairing/colour.ex:216`: `Map.fetch!(numbers, first.tpn)` in a
function whose `@doc` invites direct use with a caller-built
`:parity_numbers`. `team.ex:201-202`: `score/2` has clauses for
`:match_points` and `:game_points` only; `pair_round/2` threads
`Keyword.get(opts, :score_mode, …)` unvalidated. Both reproduced;
`pair_round/2`'s `@doc` promises `{:ok, _} | {:error, _}`.

Fix: validate at the public boundary and raise a named error.

### M6 · No CI

There is no `.github/`, no workflow, nothing that runs `mix test` on push.
The suite is 360 tests and takes 13 seconds. The OpenPairings half of this
sweep found its Elixir CI red for four pushes over a single seed-dependent
test; here nothing would have gone red at all. Twenty-three commits sit on
`feature/team-pairing` (3 ahead of `origin/main` today) with no automated
run behind any of them.

Fix: the OpenPairings `elixir.yml` minus the artifact exclusions, with the
JaVaFo/bbpPairings comparisons excluded the way `test_helper.exs` already
excludes them.

### L1 · Trailing spaces on `XXA` invent a round

`trf.ex:1678`: `String.length(line)` untrimmed, `div(length - round1_end,
5) + 1`. Five trailing spaces → a phantom `0.0` acceleration; trailing
non-space → a misleading `ValidationError`. `parse_games/1` trims first
and says why.

### L2 · Log verbosity is VM-global

`log.ex:59-64`: `Application.put_env(@app, :log_level, …)`. One process's
`set_level` changes every process's. OpenPairings never calls it and pairs
categories sequentially, so nothing is affected there; a host that pairs
concurrently would interleave trace output.

### L3 · The wrong line type in an error message

`trf.ex:1610`: `round_field!/3` is shared by `parse_260/2` and
`parse_250/2` and always says "260 line has an unreadable round number".

### L4 · `GACRUX_TIMEOUT` in a shell string

`test/support/gacrux.ex:97`: `"exec timeout #{timeout_seconds()} …"` into
`sh -c`. Everything else in that call goes through `"$0" "$@"`. Test-only,
operator-set variable; validate it is an integer.

### L5 · A docstring that no longer describes the code

`weighted_matching.ex:1092-1094` lists `outer_vertices/1` (does not exist)
and `grow/1`'s `Enum.find` (gone; `grow/1` reads `state.min_outer`, which
`offer_min_outer/2` tie-breaks canonically) as consumers protected by the
sorted `state.tops`; the one consumer that still needs protecting (M1)
does not read `tops` at all.

### Leads

**Ld1.** `blossom_ids_to_root/2` (`:2443-2459`) and `path_to_target/4`
recurse by `Map.fetch!` on `blossom_match`/`label_edge` with no depth
budget, where `augment_until_done/1` (`2n+5`) and `grow/1` (`4n+20`) both
raise rather than hang. No trigger found; the file's history records this
class hunted twice. A `2n` backstop is cheap insurance.

**Ld2.** `field_index` (`pairing.ex:1901-1908`) is `Map.new` over
`p.rank`; duplicates keep the last. Traced: it feeds only the rank-spread
addend of `edge_weigher/3`, the lowest rung, never vertex identity - so
degraded tie-break magnitude for the colliding pair, nothing corrupting.
Whether `Trf.parse/1` already refuses duplicate ranks was not checked.

**Ld3.** `select_upfloaters(_, [], _, _)` returning
`{:error, :no_upfloaters_available}` appears unreachable from
`pair_round/2` because `remaining` stays even; it is `def`, so a direct
caller can reach it. The evenness invariant was checked by hand across
`assign_bye/2` and `do_pair_brackets/4` and holds.

## Checked and clean

* **Termination.** `bracket_loop/6`'s "nobody in the last bracket can play
  anybody" case stops immediately (`next_group == [] and new_pairs == []`);
  `augment_until_done/1` and `grow/1` have explicit budgets that raise;
  exchange stages 5-7 are bounded `reduce_while`s; `new/3` and
  `build_oracle/3` at n = 0 and 1 fold empty ranges without crashing.
* **Weight packing.** Every `{value, span}` component `edge_rungs/6` emits
  stays inside its span at the minimum field size that reaches it;
  `repair_criteria/3`'s nine-rung Horner ladder is exactly `s^9`;
  `solve_local/1`'s declared ceiling has orders of magnitude of headroom.
  The hardcoded `* 1_000_000` version that once overflowed is gone.
* **Process dictionary.** All thirteen keys are set and cleared
  symmetrically in `try/after` in every entry point (`pair_next_round/2`,
  `pair_later_round/2`, `explain_round/3`) - August's #1/#2/#6 stay fixed.
  Team pairing uses none at all.
* **The August fixes, re-verified in current source**: `points_for_game/2`
  special-cases `{nil, "+"/"U"}` and `{nil, "-"}`; `eligible_for_bye?/1`
  uses the opponent-aware disjunct; `XXC white1`/`black1` are read;
  `render/1` pads the last round block; `-c` counts through
  `participated_in_pairing?/1`; the CLI rejects unknown and space-separated
  options; `even_up_exposed_duals/1` has the ported `descend_to_adjustable/3`
  and a `raise` backstop; CRLF, LF and bare `\r` split uniformly.
* **`Sequence` and `Matching` are test-only oracles** - no production
  caller - so their factorial and `2^n` costs cannot hang a tournament.
* **`hd/1` and `Enum.min/1` call sites** (`pairing.ex:418, 438, 588,
  2018-2019, 4296`): each guarded by a pattern or an exclusive `[]` branch.
* **`final_round_topscorers?/2`** re-derived by hand at the three-round
  minimum; reads `@played_key`, not `length(a.games)`.
* **C.04.3 rules the corpus cannot exercise**, checked in code: Article 1.2
  filters to played games before colour statistics (matching bbpPairings);
  C2 bye eligibility on `0000 - +`/`0000 - -` uses the fixed disjunct;
  Article 4.3's exchange order is the known open conformance item and is
  likely why M1's ties are common. No "pending forfeit" state exists to
  mishandle.
* **No atom, code or command injection surface** from file content anywhere
  in the slice; the harness adapters pass an argument list and a temp file
  path, never content, to their binaries.
* **`completable?/3` is sound**: it never rejects a branch `walk_bottoms`
  would accept - H6 is cost, not correctness. `Matching.feasible?/2`'s
  bitmask arithmetic traced by hand.
* The documented team-pairing scope exclusions (board order, cross-board
  colour alternation, team ratings) and the already-tracked conformance
  gaps in `docs/conformance-c0406-teams.md` are not re-reported.
